Aster — Deployments · production
Local-first No accounts, no telemetry, no remote web server. The app talks to your cluster and nothing else.
Your permissions Aster uses the RBAC already in the selected context. It never creates ServiceAccounts or Roles for you.
Read-only by default Every context starts read-only. Writes stay off until you explicitly turn them on.
Apache-2.0 Open source, self-contained, and auditable end to end — Electron shell, Go sidecar, and all.

Built for deliberate cluster work.

Density where you need it, restraint where you don’t. Every surface is designed to keep large clusters responsive and every change understandable.

Every resource, one fast table

Native Kubernetes pagination, label selectors, and a virtualized grid keep namespaces with thousands of objects smooth. Scoped watches stream changes in — no global informer cache, no startup sync storm.

⌘K for everything

Switch contexts, jump to any resource kind, run actions. The command palette keeps your hands on the keyboard and your place in the list intact.

Review the diff before anything happens

Scale, image updates, and restarts run through a server-side dry-run first. Aster shows a semantic diff, checks the resource version, and applies only when you say so.

# dry-run · Deployment/api-server replicas: - 3 + 5 image: - api:1.4.1 + api:1.5.0 ✓ dry-run passed · rv match

Bounded logs & one-shot terminal

Log reads are tail-limited and capped at 4 MiB. Terminal commands run once, with argv validation and a 1 MiB output cap. No persistent shell, no follow stream.

A journal of what changed

Every write lands in a per-context operation journal — summaries only, never command contents or credentials. Answer “what did I change last Tuesday?” in seconds.

Context that survives detail work

List state, scope, selection, and scroll position stay put while you inspect YAML, Events, and related objects. Pick up exactly where you left off.

⌘K to jump anywhere

Credentials stay on your side of the glass.

The renderer never sees kubeconfig contents, tokens, Secret data, or the sidecar address. A narrow, authenticated path is the only way to the cluster.

Questions, answered plainly.

Where do my credentials and kubeconfig go?+
Nowhere. Aster reads your default kubeconfig to discover contexts, but file contents, tokens, and Secret data stay inside the Electron main process and the local Go sidecar. The renderer — the part that draws the UI — never receives them.
Does Aster phone home or collect telemetry?+
No. There is no account system, no analytics, and no remote server. The only network traffic is between the local sidecar and the Kubernetes API servers in your own kubeconfig.
What can Aster change in my cluster?+
Contexts start read-only. If you enable writes, Aster supports a reviewed set of mutations — scale, image update, and restart for Deployments, StatefulSets, and DaemonSets, plus ConfigMap and YAML edits. Each goes through a server-side dry-run with a diff preview, and Secret mutation is disabled entirely.
Will it stay fast on a large cluster?+
That is the design center. Aster uses native Kubernetes pagination and selectors, a virtualized table instead of full-list rendering, and lazy per-view clients. There is no global informer cache and deliberately no “load everything” option.
How is this different from a web dashboard?+
Aster is a desktop workbench, not a hosted control plane. It feels native on macOS, keeps your working context across detail views, and adds safety rails — read-only defaults, dry-run diffs, and an operation journal — instead of another place to paste admin credentials.
